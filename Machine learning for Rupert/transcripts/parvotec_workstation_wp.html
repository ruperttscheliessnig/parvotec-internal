Why Local Infrastructure — Not Cloud

The DRG Fitness Oracle pipeline operates on proprietary sequence–fitness data that cannot leave a controlled environment under standard industry agreements. Cloud GPU instances (AWS p4d, Azure NC, GCP A100) introduce three structural problems for this project:

1. Data sovereignty. Biological assay data from DRG partner institutions is covered by material transfer agreements (MTAs) that restrict transfer to third-party compute providers. A local workstation is the only compliant option.

2. Continuous training economics. WP2 requires ~1,200 GPU-hours of ESM-2 embedding at €2–4/GPU-h on cloud = €2,400–4,800 for one work package alone. WP4 adds ~2,400 GPU-h = €4,800–9,600. Total cloud cost over 24 months: €15,000–25,000, exceeding the workstation purchase price and offering no long-term asset.

3. Iteration latency. Active learning in WP4 requires tight embed → train → propose → wet-lab cycles. Cloud cold-start latency (5–20 min per instance) and scheduling uncertainty breaks the 72-hour turnaround that fits within the wet-lab's compound synthesis cycle.

WP1 · Target Definition (M1–M3)

Objective: Identify the DRG-relevant sequence space. Use ESM-2 (650M) embeddings on 100–500 pilot sequences to validate the fitness signal and define the fitness assay protocol.

This phase is low-intensity but sets the calibration baseline for all downstream models. A GPU is required to run ESM-2 in batch mode; CPU inference is 40× slower and would push pilot timelines from hours to days.

Compute requirement:

  • ESM-2 650M inference on pilot set: ~20–40 GPU-h (RTX-class, 16+ GB VRAM)
  • Embedding storage: <2 GB per 500 sequences
  • No training in WP1 — inference only
  • CPU fallback: 40–80 GPU-h equivalent → ~2 weeks on CPU vs. 2 days on GPU

WP2 · DMS Library Construction (M2–M8)

Objective: Generate and embed a Deep Mutational Scanning (DMS) library of ~500,000 AAV capsid variants using ESM-2. This is the largest single compute task of the project.

ESM-2 must process each variant independently (no batching across unrelated sequences at this scale). A single RTX 5090 (32 GB VRAM) can run batch sizes of 64–128 at FP16, completing the full library in ~72 hours of continuous GPU time. Without local infrastructure, this would require renting a dedicated cloud instance for 3 continuous days — impractical at research-budget scale.

Compute requirement:

  • ESM-2 650M, 500k sequences × ~2.4 ms/seq at FP16 → ~333 GPU-h
  • Embedding cache: ~250 GB (1280-dim × 500k × fp16)
  • Must run 24/7 uninterrupted — cloud scheduling risk unacceptable
  • Intermediate checkpointing every 50k sequences for fault tolerance

WP3 · Oracle v1.0 (M4–M10)

Objective: Train the 4-Task Predictor Neural Network (Tropism, Yield, Thermostability, Immunogenicity) and the Conditional VAE (cVAE) on the embedded DMS library from WP2.

These are training tasks, not just inference. The 4-task NN operates on pre-computed ESM-2 embeddings (no GPU needed for forward pass from WP2 cache) but backpropagation through the multi-task head requires sustained GPU memory. The cVAE additionally needs the GPU for its KL-divergence regularized latent space optimization — a compute pattern that benefits strongly from FP16 tensor cores.

Compute requirement:

  • 4-Task NN: ~150 GPU-h (32-dim hidden, 4 output heads, MSE + cross-entropy)
  • cVAE: ~100 GPU-h (encoder 512-dim, decoder 512-dim, KL weight schedule)
  • Hyperparameter sweeps: ×3–5 multiplier → plan for 750 GPU-h total in WP3
  • Both models fit in 16 GB VRAM; RTX 5090 enables larger batch = fewer epochs

WP4 · Bayesian Optimization Rounds × 3 (M8–M18)

Objective: Run three active-learning cycles: propose candidates → synthesize → assay → retrain. Each cycle requires a full re-embedding + Oracle retrain + BO acquisition, all within a 4-week wet-lab turnaround window.

This is the critical-path bottleneck. Each round must complete its compute within 72 hours so the wet-lab team can order synthesis without delay. A cloud instance would add 5–20 minutes cold-start plus potential preemption risk. The local workstation guarantees on-demand availability at 03:00 when a training run finishes and the BO acquisition needs to start immediately.

Compute requirement per round:

  • ESM-2 re-embedding of new assay data: ~120 GPU-h
  • Oracle retrain (fine-tune from WP3 checkpoint): ~50 GPU-h
  • BO acquisition function (Gaussian Process): CPU-dominant but GPU-accelerated via GPyTorch
  • 3 rounds × ~800 GPU-h = ~2,400 GPU-h total
  • Must not be interrupted — any preemption resets the 72-h clock

WP5 · Lead Validation (M14–M24)

Objective: Transfer-learn the Oracle on the top-candidate set from WP4. Run structural predictions (AlphaFold2/ESMFold) on leads. Prepare final model for partner delivery.

WP5 is lower intensity but benefits from the same hardware. AlphaFold2 inference for 10–50 candidates requires 40 GB VRAM per complex (or chunked 16 GB runs). ESMFold is lighter. The workstation GPU serves as the inference node for final validation without additional cloud cost.

Compute requirement:

  • Transfer learning on top-50 leads: ~50 GPU-h
  • ESMFold inference (structural validation): ~10 GPU-h
  • Final Oracle inference for deliverable: ~5 GPU-h
  • Total: ~300 GPU-h spread over 10 months (~30 GPU-h/month)
